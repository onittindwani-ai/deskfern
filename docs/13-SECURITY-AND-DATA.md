# Security and data

The full list of what was tested and what was not is in `../SECURITY.md`. In short:

- **Refunds need two people.** The desk can only ask. A different person approves a refund that a person asked for (it is asked in that person's name). A refund the worker asks for by itself is asked in Deskfern's name, so the owner or the approver decides it; a live install that can pay refunds therefore must have a separate approver login (`APPROVER_EMAIL`), or the app refuses to start. Only after the approval does the payment adapter act, once, and never in draft mode or when the kill switch is on. A refund approved while one of those was on is kept as approved, not paid yet, and is paid once both are off (the worker checks every minute, or press Pay approved refunds on the Approvals page).
- **Draft mode is the default.** Nothing is sent or paid. Live mode is a setting changed outside the app.
- **Customer text is data.** Text in a ticket that tries to give orders ("ignore your rules", "refund me now") is flagged and never obeyed.
- **One customer's data never goes to another.** A ticket that asks about someone else's account is handed to a person.
- **Website crawling is guarded.** Only public addresses, redirects are checked again, robots.txt is respected, and size, depth, page, time and total size limits apply (a site's Crawl-delay is capped at 10 seconds). The worker runs the crawl, so a slow or hostile site cannot hold up a web request.
- **Audit log.** Every change is chained to the one before. Press Check the chain on the Audit page.
- **Web.** The browser never holds a vendor key. The web app forwards to the API and adds a required header to every change, so a form on another website cannot make the browser change data.
- **Who a message is really from.** Anyone can type any address into a message. The desk only treats a sender as a known customer when it could check it: for email, your mail provider must have added an `Authentication-Results` header (the top one, starting with the name in `INBOUND_AUTHSERV_ID`) that says `dmarc=pass`; for a helpdesk channel, the channel must be listed in `TRUSTED_SENDER_CHANNELS`. A message that fails this is kept, flagged `unverified sender`, never linked to a customer, and answered with a short note asking the person to confirm their address (a person on your team confirms it on the ticket before any private fact is used). Turn the rule off only by setting `REQUIRE_VERIFIED_SENDER=false`, which you should do only when every sender is already known to be real. Where to find your provider's name: `04`, under `INBOUND_AUTHSERV_ID`.
- **Bad input stops at the door.** A request over `MAX_BODY_BYTES` is refused as it arrives. A message with an unreadable character set, a very long identifier or other data the database refuses is skipped on its own without stopping the others, and what it said is never written into a log.
- **Email.** The inbox and the sender connection check the certificate and the host name. A plain connection is accepted only to a mail server on the same computer. What is new is decided by the message's number in the mailbox (its UID, with the mailbox's UIDVALIDITY), not by the unread flag: mail a person opened on a phone before the next run is still taken in, and a mailbox that refuses to mark mail read cannot make the same 50 messages come back. The first run reads the mail that is unread at that moment and nothing older; after that every message with a higher number is read. One run reads at most 50 messages and skips any over 2 MB without downloading them (they are listed in the run result and stay in the mailbox for a person); a mail with only an HTML part is read as plain text. Mail is marked read after it is stored, as a courtesy to your team; repeated failures to do so are shown in the settings problems.
- **Replies are sent once.** The answer is marked as being sent, and that is saved before anything leaves. If the helpdesk or the mail server does not confirm in time, the ticket asks a person whether the customer got it (It was delivered or It was not delivered) instead of sending again. A reply that draft mode or Pause all stopped is held, and the ticket stays open. A reply that left (as it was, or with an edit) is never sent a second time, whatever the ticket is moved to afterwards, and Draft again is refused while a send waits for a person to say whether it was delivered.
- **Sign in.** Sign in is limited per address, per address and account, and per account from anywhere. The account wide limit counts failed tries only and never holds up an address that signed in as that account in the last 24 hours. A browser that signed in before carries a signed note (an httpOnly cookie, only made after a verified password) and its tries are counted on their own, so someone failing at the owner's account from a shared address cannot lock that browser out. While an attack on the account is running, a first sign in from a browser that never signed in can wait; see `../SECURITY.md`. If the API cannot tell visitors apart (set `FORWARDED_ALLOW_IPS`, see `06`, `07`, `08`), the settings page says so. `SESSION_SECRET` must be a real value whenever an owner password is set or MODE is live.
- **Erasing and keeping.** The owner can erase one customer on request (`POST /api/customers/erase`, or `python -m deskfern.admin erase-customer person@example.com`): their tickets' words, answers, hand over notes, test cases made from their edits and their customer record go; a ticket that a refund record points at stays as an empty shell; only a salted hash of the address is kept, so importing the customers file again or a new message from that address does not bring them back. Finished tickets older than `RETENTION_DAYS` (default 730) lose their words the same way, once a day. The audit log records that an erase happened, never the address. Backups made earlier still hold the data until they are rotated out; see `11`.
- **Where data lives.** Tickets, customer names and answers are in your database. If you later connect a language model, the ticket text and the cited passages go to that vendor.

## What you must do

Keep `.env` out of Git. Use a second approver. Back up the database and the knowledge folder. Rotate a key if you ever pasted it somewhere. Keep the server updated.
