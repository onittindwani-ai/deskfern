# Limits and honest notes

- **The live model path has never run with a real key (UNVERIFIED).** The code behind `LLM_BACKEND=anthropic` writes the reply sentences, can judge a gray sentence, adds a second look to the triage and words suggestions and Insights numbers. It was run only against a local mock server that checks the request shape, and against recordings made from that mock server. How a real model writes your replies, what it costs per ticket and how often it is wrong are unknown. The code checks around it (unsupported sentences removed, no refunds or sending by a model, orders in tickets and pages kept out) are tested; see `facts/models.md`.

- **The demo answer writer is a stand in, not a language model.** It picks sentences. On a held out set of 63 questions written before the code, it answered 13 correctly on the first run. It over hands tickets to people and misses questions worded differently from the pages. This is measured in `ANSWER-EVAL.md`, and on two independent sets in `INDEPENDENT-EVAL.md` (about 6 in 10 tickets read right on the first run, and it still answers some tickets that need a person when a nearby page exists). A real model or real embeddings may do better or differently, and that was not measured.
- **The groundedness checker was tuned on a set its author labelled**, so its precision of 1.0 on 79 labelled sentences is not an independent score. The first, untouched run was precision 0.893 and recall 0.625.
- **Search similarity is a hashed bag of words**, not a language model embedding. The Postgres full text path and the migration up, down, up cycle were run once in a throwaway local Postgres 17 (seed score 86 of 121 against 83 on SQLite; the ranking differs). The full test suite and the browser tests ran on SQLite only.
- **No real vendor was contacted.** Adapters were tested against local imitations. Vendor page names and steps in the guides are marked UNVERIFIED where they were not read.
- **Deploy files were never run on a real host.** The CI workflow builds the Docker images and starts the compose stack on a GitHub machine, which shows they build and start, nothing more. No Hetzner, Railway or Vercel account was used. The Caddy, backup and cloud-init files are checked only for syntax and from our general knowledge.
- **Postgres specific hardening is untested on a running Postgres.** Skipping a message whose text a Postgres refuses (a zero byte, a value over its column length), a very long search word and the savepoint handling were written from how Postgres behaves and run on SQLite. Run the suite once with `TEST_POSTGRES_URL` set before you rely on them.
- **Crawling is guarded but not pinned.** The address is checked before each request and the connected address is checked after, but the connection is not forced to the address that was checked. A real site is crawled by the worker, with limits on time, size and the pause between pages.
- **Helpdesk lists are read up to 5 pages per run.** Intercom, Zendesk and Freshdesk are followed page by page through the vendor's own paging pointer (written from memory of the public docs, UNVERIFIED against the live services, tested against local imitations). Zendesk is asked for the newest tickets first (`sort_by=id&sort_order=desc`, UNVERIFIED against a live Zendesk) and the desk remembers the highest ticket number it handled, so a long history does not hide new tickets; if more than 5 pages of new tickets arrive between two runs, or Zendesk does not sort as asked, the run says so and the older ones must be opened in Zendesk. Intercom and Freshdesk lists are read from their start each run, so check on the first day that new tickets arrive if your helpdesk holds more than 5 pages. Closed and snoozed Intercom conversations, and resolved or closed Freshdesk tickets, are not imported. A ticket that cannot be stored is tried again each run (the Zendesk position stays just below it) and after 3 runs becomes a ticket that needs a person; an answer that is not data, or a list entry with no usable number, is named under Needs attention on the Queue and in the settings. A list entry with no number cannot become a ticket, so it is counted, not kept: open the helpdesk to see it.
- **A mailbox run takes 50 messages and does not download any over 2 MB whole.** The rest wait for the next run. A large message is read through its text part alone (its structure is asked for first), so a screenshot or a PDF does not make a mail unreadable; one whose text part is itself over 2 MB, or that has no readable text part, becomes a small ticket that needs a person. New mail is found by its message number (UID) and the mailbox's UIDVALIDITY, not by the unread flag, so mail opened elsewhere is still taken in. The first run reads only the mail that is unread at that moment; older read mail is never imported. A message the desk cannot read at all is also a small ticket that needs a person, with the sender and subject when its header could be read and none of its words; the original stays unread in the mailbox. If the mailbox is renumbered the unread mail is read again, and mail already stored is recognised, not duplicated. Written against a local imitation of IMAP, UNVERIFIED against Gmail or Outlook. That includes the new way a large message is read (its BODYSTRUCTURE and then its text part alone): it is tested only against the repo's own mock server, and a structure the desk cannot read, such as one a real server writes with a literal inside it, makes the message a ticket for a person instead.
- **A reply that was not confirmed needs a person.** After a timeout the desk cannot know whether the customer got the reply, so it asks you to check the helpdesk or the mailbox. This is deliberate: guessing would send some customers two copies or none.
- **Sign in under attack.** The owner's usual address, and any browser that signed in before, is never held up by someone failing on purpose at the owner's account, but a first sign in from a new browser can wait while it goes on. Behind a proxy whose forwarded address the API does not trust (`FORWARDED_ALLOW_IPS`), every visitor looks like one address and a stranger can hold up a first sign in from a new browser until they stop; set it as docs 06, 07 and 08 say.
- **Erasing one customer is built for the API and the command line, not as a button.** It removes tickets, answers, hand over notes, test cases and the customer record, keeps refund records as empty shells, and remembers only a salted hash of the address, also on each refund record (so the 12 month refund rule survives a lifted erasure and a new import). A later message from that address becomes a minimal ticket for a person until the owner lifts the erasure (`python -m deskfern.admin lift-erasure`). Pages you pasted or crawled that quote a customer are your own content and are not touched, nor are older backups (docs/11). Removing a page you deleted from `KNOWLEDGE_DIR` is not built (delete it on the Knowledge page instead).
- **Languages:** the demo has five non English tickets and handles them by handing over. Replies are drafted in English.
- **Not built:** a Drive token refresh, attachments in tickets, voice, chat widget, multi brand setups, and any automatic change of your help pages.
- **Scores for health and churn** are simple rules with sample examples, not predictions.
- **The one refund per 12 months rule** counts the number in your customer file plus the refunds the desk itself asked for, approved or paid in the last 12 months on other payments. The retention job keeps the link between an emptied ticket and its customer, so a `RETENTION_DAYS` under 365 does not lose that history (the settings page warns anyway). If your billing file already counts a refund the desk paid, the customer is counted twice (the safe side). A re-import with no `refunds_12m` column keeps the number the desk has.
- **Refund amounts** above your limit always need a person. The limits in the demo are defaults, not your rules.
- **SQLite allows one writer at a time.** In the browser test run a log line showed a database lock error once while the demo clock job ran next to another request (the tests still passed). Use Postgres for more than a few people.
- **Intake notes are shown for 7 days.** What a run noticed (a gap in a helpdesk list, skipped mail) stays on the Queue and in the settings for a week, then disappears; a helpdesk that answered with something unreadable is listed until its next good run. The small tickets stay until a person closes them.
- **The web unit tests are not in CI.** `make test` runs them (`pnpm --filter web test:unit`), and the CI workflow does not yet, so a browser side regression in the proxy helpers is only caught on a developer machine until the shared CI template adds it.
